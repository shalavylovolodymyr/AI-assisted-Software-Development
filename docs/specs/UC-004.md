# UC-004 — Mitigate, resolve and reopen

## Intent
Close issues only with evidence that corrective work and residual risk were reviewed.
## Actors
Known selected demo user.
## Preconditions
Existing issue, current version supplied, explicit target status.
## Inputs
Issue UUID, target status, expected version; actor from demo identity header.
## Flow
1. Lock issue and check expected version.
2. Allow OPEN→IN_PROGRESS; IN_PROGRESS→OPEN/MITIGATED;
   MITIGATED→IN_PROGRESS/RESOLVED; RESOLVED→IN_PROGRESS.
3. MITIGATED requires a plan and all non-cancelled actions DONE.
4. RESOLVED requires at least one DONE action and a risk assessment strictly
   after the latest required completion. Recheck completion conditions.
5. Set resolved_at and write audit atomically; increment version.
6. Reopening clears resolved_at, retains all history and adds reopening audit.
## Alternative flows and errors
409 invalid/duplicate/stale transition, incomplete action, missing/stale reassessment;
404 missing issue/actor. Failure has no audit or state side effects.
## Postconditions and acceptance
Eligible issue resolves with timestamp. Ineligible resolution explains exactly why.
Reopened issue retains assessments and action evidence, with resolved_at cleared.
## Tests
Unit: every status pair, missing/all-cancelled/incomplete actions, equal/outdated
assessment timestamps, reopen. Integration/API: atomicity, concurrent writes,
complete workflow. E2E-003 resolves; E2E-004 verifies incomplete-work rejection.
## Non-functional
Backend is authoritative. UI offers valid targets and renders domain errors accessibly.
