# UC-005 — Delete and restore issues and unfinished actions

## Intent
Remove unwanted work from current views while preserving its records and audit history.

## Actors and scope
ADMIN/MANAGER; a MEMBER may remove/restore issues they report or own, and actions
they own. This extends the prior no-deletion scope with reversible removal only.
Assessments, comments, audit events, DONE and CANCELLED actions remain immutable.

## Flow and rules
1. Lock the parent issue and validate the expected version and known actor.
2. Set or clear the record's deletion timestamp and append its audit event atomically.
3. Increment the parent version. Duplicate operations and stale writes fail without effects.
4. Deleted issues remain readable, with history intact, but block business mutations.
5. Delete/restore actions only on a current OPEN/IN_PROGRESS issue; only TODO or
   IN_PROGRESS actions can be removed. Restore retains the original action status.
6. Current registers, risk/matrix, queues and snapshot analytics exclude removed work.
   Deleted views expose recovery. Restoring an issue retains its children and status.
7. Trend history reflects deletion/restoration from each recorded event onward.

## Acceptance and validation
Test-first pure Application tests cover removal/restoration, authorisation, stale
versions, failed commits, mutation guards, history retention and snapshot/trend
visibility. Isolated PostgreSQL/API tests verify persistence and route contracts.
Browser checks traverse issue/action removal and recovery without success popups.
No production data is removed during implementation or verification. Loading the
new API remains subject to the owner's instruction to keep the existing API running.
